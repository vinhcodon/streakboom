## 1. What SignPath gives, and what it asks

Free Authenticode signing for qualifying open-source projects: a certificate **issued to SignPath Foundation** (Windows shows that name as the publisher; no personal identification is needed from you; the key sits in SignPath's hardware module). In exchange it verifies that **each signed binary is an automated build of the public repository**, and **every release needs a manual approval** in SignPath. As with any certificate, SmartScreen reputation still builds over time ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options)); the alpha testers will probably still see a prompt.

## 3. The release flow in CI (decided: a hybrid, the updater key stays on the author's computer)

```
tag vX.Y.Z pushed
  -> CI (GitHub-hosted windows-latest): checks (tag = tauri.conf version, CHANGELOG entry), tests, build the NSIS installer
     (without the updater key: createUpdaterArtifacts off), upload it as a workflow artifact
  -> [after approval] SignPath: the signing request is made from the artifact; the author approves it in SignPath;
     the signed installer comes back
  -> CI: a DRAFT GitHub release with the (signed) installer and the notes of the CHANGELOG
  -> the author, on his computer: scripts/release-finish.ps1
       downloads the installer, checks its Authenticode signature (when signing is on), signs it with the updater key
       (the minisign key that never leaves his computer), writes latest.json, uploads it, publishes the release,
       commits and pushes updates/latest.json, prunes the old releases
```

- **Why a hybrid:** the updater signature must be made **after** the Authenticode signature (it covers the final bytes), and it needs the private updater key, which today never leaves the author's computer. SignPath's manual approval already puts a person in every release, so the last local step costs little.
- **Before SignPath is approved** the same flow runs without the signing step: CI builds and drafts the release, and the author finishes it. That is what makes the first CI releases possible (and gives the public build history the application needs).
- **Safety of the pipeline** (SignPath reads the CI configuration as source): actions pinned to a commit, `permissions` as small as possible, the release job only for tags pushed by the owner, the signing step only from the official repository, and build provenance attestation (GitHub's, free for public repositories; **not verified**) as an extra.
- **What is signed:** only the final NSIS installer, the file people download. The program inside (`streakboom.exe`) and the uninstaller are **not** signed by this flow (Tauri's bundler signs while it bundles; SignPath answers later, after approval, so it cannot be called inside the build). Signing them too needs a build in two stages (build the exe, sign it, then bundle). It is a later improvement, not a condition of the application.

## 5. Reputation: the main risk, and what we can honestly do

SignPath asks for "a certain verifiable reputation" for executable programs and gives no number; projects report that a website, a few stars and some public presence help, and some were turned down. Today we have the website, a documented project, a public CI history (after step 4) and 16 downloads. What can raise it without pretending: the alpha and the Vietnamese sticker test bring real downloads; the README and the site are in good order; a short, honest note in the places where Vietnamese developers read; ask the alpha testers who like it to star the repository (not before they have used it). Nothing is bought, and nothing is asked in a way that is not true.

**If the application is declined (the free plan B):** stay unsigned and keep the "More info, Run anyway" steps in the install guide; reapply later when the project has users (the rules for reapplying are **not verified**); or, as a separate and larger project, publish through the Microsoft Store (MSIX), where Microsoft signs for free ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options)). Paid certificates are out of scope by the author's decision.

## 5b. What the SignPath documentation says about our pipeline (read 2026-11-13, not tried)

- **The action** (`SignPath/github-action-submit-signing-request` v3.0, its `action.yml`): the inputs `api-token`, `organization-id`, `project-slug`, `signing-policy-slug`, `artifact-configuration-slug`, `github-artifact-id` (from the upload step's `artifact-id`), `parameters` (one `name: "value"` per line), `wait-for-completion` (default true) with a **default wait of 600 seconds**, and `output-artifact-directory`, into which the signed archive is **extracted** unless `skip-decompress` is true. The workflow now waits up to 5400 seconds (the approval is by hand) and reads `signed/<installer>`.
- **The artifact configuration** (XML, schema `http://signpath.io/artifact-configuration/v1`): a `zip-file` (the uploaded artifact is a zip) with one `pe-file` that matches the installer by a pattern (`Streakboom_*_x64-setup.exe`; it must match exactly one file) and carries `product-name` and `product-version` (the version is passed as a parameter) and `authenticode-sign`. The example is in the comment of `release.yml`.
- **Runners:** for open-source projects SignPath checks that every job before the signing request ran on GitHub-hosted runners (ours does).
